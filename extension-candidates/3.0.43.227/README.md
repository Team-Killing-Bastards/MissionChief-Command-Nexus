# Nexus 3.0.43.227: automatic dispatch and loading recovery

Based on .226 (`997631ed861e42dcc216854a094ac6955c27a0f6`). Retains background event collection, OSU-first HazMat alternatives and ATC/ARV/Police priority. No store submission.

## Evidence and correction

Both supplied user exports ran .223. The store update was .205 to .223. They recorded 49 and 60 hard post-dispatch recoveries. The retained 15 October trace for mission 264413808 shows final Dispatch at 11:42:35.189 UTC, a same-route replacement document at 11:42:35.924, then soft/hard recovery at roughly 5/16 seconds. The old final-handoff function waits 800 ms; navigation can dispose that function first. The replacement runtime's pending-dispatch guard blocks selection correctly but also prevents the loop's final-queue handoff. A pending personal radio request also prevents the ordinary low-queue pause. The new controller handoff accepts only a fully loaded, confirmed, currently owned replacement document with a matching unexpired claim older than that document. It retains the claim, prioritises transport, opens another mission or waits for supply. It never repeats Dispatch. Submitted missions still shown as actionable retain the ordinary uncertain-result deferral. Same-document requests, active selection/startup, transport, explicit Stop and mismatched ownership do not use the shortcut.

The older export retains 16 vehicle-list failures. The old wording “No units were selected” was classified as a resource shortage, but did not satisfy the pre-dispatch recheck wording. It therefore never got that fresh-page retry and waited for 20 mission advances. Fourteen failures shared advance counter 262. Loading failures now have a separate category: after a three-second confirmation, one fresh load is allowed only without a dispatch claim. Persistent failures yield to other missions and use a one-minute timed cooldown, rising to at most five minutes. Expiry does not require successful mission advances. Existing per-mission recovery-attempt bounds remain. Genuine shortages keep their existing handling. Exports retain the loading reason and row/page counts; the UI shows timed eligibility. This addresses recovery from loading failure, not every possible game/network/third-party cause of a failed load.

## Coverage and performance

Pagination, list stability, partial-load coverage proof, full-list fallback, vehicle selection/counts, trained-occupant checks, seat limits and final dispatch gates are unchanged. Healthy missions gain no deliberate wait or extra request. The recovery test reads one existing final-dispatch flag on the existing controller tick; deeper proof runs only at that boundary. No new timer, observer or background scan is added. Existing bounded recovery history is reused and contains scalar data only.

`check-auto-recovery.mjs` reproduces the old final-claim rejection and loading misclassification; exercises once-only continuation, transport priority, current-document/ownership/manual-stop guards, claim retention, one fresh loading attempt, timed expiry without advances and bounded backoff; compares protected coverage functions byte-for-byte. `check-auto-recovery-browser.mjs` uses real same-route form navigation in an isolated Edge profile with every request intercepted. It verifies one native POST, automatic navigation to the next mission and no repeated dispatch. Existing throughput, crew, alternatives, startup, idle dispatch, patient-tail, Any vehicle, CRV and event collection regressions also run against this candidate. Fixture timing is not a live throughput measurement.

## Install

Stop Auto Mode, extract `Nexus-3.0.43.227-Automatic-Recovery.zip` into a fresh folder, update the unpacked extension and refresh every MissionChief tab. Confirm .227 before restarting Auto Mode. Existing settings, profiles and Discord identity remain unchanged. A live endurance run is still required to verify the user's game/network conditions; export after the run or immediately if a stop remains.
